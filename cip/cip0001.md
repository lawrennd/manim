# CIP-0001: SVG Renderer for Web Export

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [ ] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

Add a new `SVGRenderer` to Manim that exports scenes as per-frame SVG files instead of rasterizing to a pixel buffer. This enables web-embeddable, scalable animations that preserve mathematical precision from the Python scene through to the browser. A small companion JS plugin provides RevealJS integration.

This CIP addresses REQ-0001 (web-embeddable animations without rasterization), REQ-0002 (RevealJS embedding), REQ-0003 (LaTeX vector preservation), REQ-0004 (unchanged authoring API), and REQ-0005 (upstream contribution readiness).

## Motivation

Manim's existing output formats are all rasterized: MP4, WebM, GIF, and PNG sequences. For web use this creates friction — video requires hosting infrastructure, autoplay policies, and codec support; PNGs don't animate. Neither format is scalable: a presentation zoom reveals pixelation.

Manim's internal geometry is already vector: `VMobject` stores Bézier curves, LaTeX is converted to SVG before import, and the Cairo renderer immediately discards this precision by rasterizing to a pixel array. The SVG format is the natural web target for this geometry — paths are Bézier curves, colors are exact, and output scales to any resolution.

`manim-slides` (an existing community tool, v5.5.4) already provides RevealJS export using video. This CIP takes a different approach: vector SVG output, targeting scenes where geometric precision and scalability matter more than video compatibility.

## Detailed Description

### Architecture

The SVG renderer plugs into the existing renderer abstraction at the same level as `CairoRenderer` and `OpenGLRenderer`. `Scene.__init__` selects the renderer based on `config.renderer`; we add `RendererType.SVG` and instantiate `SVGRenderer` when selected.

```
Scene.play_internal()
  └─ update_to_time(t)          # existing: advances animation state
  └─ SVGRenderer.render(t)      # new: replaces CairoRenderer.render
       └─ SVGCamera.capture_mobjects()   # new: walks VMobject tree → svgwrite.Drawing
       └─ SceneFileWriter.write_svg_frame()  # new: saves frame_{N:04d}.svg
```

The frame loop in `Scene.play_internal` is unchanged. `SVGRenderer.render` is called with the same signature as `CairoRenderer.render` — it just writes SVG instead of passing a pixel array to PyAV.

### SVGCamera: VMobject to SVG Path Conversion

`SVGCamera.capture_mobjects` walks the mobject tree in z-index order and dispatches on type:

**VMobject** (circles, lines, arrows, polygons, etc.):
- Extract cubic Bézier handles from `vmobject.points` (groups of 4: anchor, handle1, handle2, anchor)
- Build SVG path string: `M x0,y0 C h1x,h1y h2x,h2y x1,y1 ...`
- Close the path with `Z` if `vmobject.is_closed()`
- Apply stroke color/width/opacity from `vmobject.get_stroke_color()`, `get_stroke_width()`, `get_stroke_opacity()`
- Apply fill color/opacity from `vmobject.get_fill_color()`, `get_fill_opacity()`
- Apply the camera's coordinate transform (Manim uses a centred coordinate system; SVG uses top-left origin)

**SVGMobject / TeX / MathTex**:
- The cached SVG file on disk (produced by `tex_to_svg_file`) is already the correct output
- Embed the SVG content inline as a `<g>` element, applying the mobject's current transform matrix
- This preserves per-glyph path elements, maintaining sub-mobject manipulability

**ImageMobject**:
- Base64-encode the pixel array as PNG
- Emit `<image href="data:image/png;base64,...">` with correct position/size

**OpenGL mobjects / 3D scenes**:
- Emit a warning and skip; document as a known limitation

### Coordinate System

Manim's coordinate system: origin at centre, y-up, default frame `[-7.1, 7.1] × [-4, 4]`.
SVG coordinate system: origin at top-left, y-down.

Transform applied per frame:
```
svg_x = (manim_x - frame_left) / frame_width  * svg_width
svg_y = (frame_top - manim_y) / frame_height * svg_height
```

Applied as a `viewBox` on the root `<svg>` element plus a `<g transform="...">` for the y-flip, so individual path coordinates remain in Manim's space and are transformed by SVG's built-in transform machinery.

### Output Format

Per animation (contiguous `self.play()` or `self.wait()` call), the output is:

```
media/svg/SceneName/
  animation_0/
    frame_0000.svg
    frame_0001.svg
    ...
    animation.json      # {"fps": 15, "frame_count": 45, "width": 1920, "height": 1080}
```

The JSON manifest is written after the last frame of each animation block, giving the JS side everything it needs without parsing filenames.

### RevealJS Plugin (js/manim-svg.js)

A ~60-line vanilla JS plugin (no build step, no bundler):

```html
<script src="js/manim-svg.js"></script>

<section data-manim-svg="media/svg/MyScene/animation_0/"
         data-manim-fps="15"
         data-manim-loop="true">
</section>
```

On slide entry: reads `animation.json`, preloads SVG frames as `<img>` elements, starts a `setInterval` cycling through them at the declared fps. On slide exit: clears the interval. The `data-manim-loop` attribute controls whether the animation restarts.

Note: this JS file lives in `js/` in this fork. When the Python renderer is stable, the JS will move to a separate `manim-svg` PyPI/npm package. It is explicitly not proposed for upstream ManimCE (which is Python-only).

## Implementation Plan

1. **Config and CLI** — Add `RendererType.SVG`, `is_svg_format()`, and `--format svg` support. Scaffold `SVGRenderer` and `SVGCamera` as stubs that produce empty SVG files. Verify the render pipeline runs end-to-end without errors on a simple scene.

2. **VMobject → SVG path** — Implement `SVGCamera.capture_mobjects` for `VMobject`. Cover stroke, fill, opacity. Verify `SquareToCircle` example produces visually correct frames.

3. **Coordinate transform** — Implement Manim-to-SVG coordinate transform. Verify alignment with Cairo output on the same scene.

4. **TeX / SVG embedding** — Handle `SVGMobject`, `Tex`, `MathTex` by embedding cached SVG inline. Verify a scene with `MathTex` produces correct vector text.

5. **ImageMobject** — Handle `ImageMobject` via base64-encoded PNG data URI.

6. **SceneFileWriter integration** — Write `animation.json` manifest. Ensure output directory structure matches the spec.

7. **RevealJS plugin** — Write `js/manim-svg.js`. Test in a real RevealJS presentation.

8. **Tests** — Write `@frames_comparison` tests for steps 2–5. Run `ruff` and `mypy`. Verify REQ-0005 acceptance criteria.

## Backward Compatibility

No changes to existing public API. `SVGRenderer` is only instantiated when `config.renderer == RendererType.SVG`, which requires explicit opt-in via `--format svg` or `config.renderer = RendererType.SVG`. All existing render paths (Cairo, OpenGL) are unchanged.

## Testing Strategy

- `@frames_comparison` tests comparing SVG-rendered output (converted to PNG for pixel comparison) against Cairo-rendered reference frames for representative scenes: `SquareToCircle`, a `MathTex` scene, and an `ImageMobject` scene
- `ruff` and `mypy` pass with no new errors
- Manual verification in RevealJS with the plugin
